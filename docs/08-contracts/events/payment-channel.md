# Payment Channel — Events & Commands

Last updated: 2026-07-10

## Scope and activation-wave rulings

This contract enumerates the ADR-0003 Wave A Payment Channel facts for simulated
channels `ALIPAY_SIM`, `WECHAT_SIM`, and `UNIONPAY_SIM`. It covers
`ChannelOrder`, `ChannelRefund`, deterministic daily `ChannelStatement`, and
`ReconciliationDiscrepancy` facts from `docs/02-domains/payment-channel.md`.

RULING (ADR-0003 Wave A): SIM gateway behavior is deterministic and seedable.
Seeded dropped-order/dropped-refund, amount-mismatch, status-mismatch,
duplicate-line, refund-lag, and statement-delay scenarios are represented as
channel facts and statement discrepancies; they do not rewrite Payment platform
money state.

All payload fields are camelCase, enum values are SCREAMING_SNAKE_CASE, and
timestamps are RFC3339 UTC. Money is `{currency, minorUnits}`. Event envelopes
follow `docs/08-contracts/messaging.md` and `docs/08-contracts/api/README.md`.
Envelope `correlationId` uses `corr-<uuid-v7>` form when generated by this
context; envelope `causationId` uses the upstream event ID or command ID, and
command causation IDs use `cmd-<uuid-v7>` form.

## Same-wave cross-context increments（需同波实现）

These events require same-wave implementation outside Payment Channel:

| Context | Increment | Required code touchpoints |
|---|---|---|
| Payment | Consumes terminal `ChannelOrderSucceeded`, `ChannelOrderFailed`, `ChannelOrderMissed`, `ChannelRefundSucceeded`, `ChannelRefundFailed`, and `ChannelRefundMissed` to decide whether to publish existing Payment facts. Capture/refund handoff carries `channelRef`. | Payment event consumer registration; `channelRef` command DTO; channel enum validation; capture/refund state guards; idempotency folding; event serializer/deserializer tests. |
| Finance Settlement | Consumes `ChannelStatementGenerated`, `ChannelStatementFrozen`, and discrepancy facts for daily channel reconciliation. | Finance consumer registration; statement payload validation; `differenceType` mapping to existing Finance `missing-in-channel`, `missing-in-platform`, `amount-mismatch`, `currency-mismatch`, `duplicate`, `late-payment`, `refund-lag` strings; consumed-event dedup. |

## Event identity and idempotency

Payment Channel producers MUST assign deterministic envelope `eventId` values per
aggregate transition. Event IDs keep UUID-v7 shape while folding stable material
into the random portion so retries do not create duplicate facts. The canonical
seed format is:

```
payment-channel:<eventType>:<aggregateId>:<aggregateVersion>:<materialHash>
```

For statement-line events the seed appends `:<statementLineId>`. For idempotent
command replay that does not apply a new transition, no new event is emitted.
Consumers still deduplicate by envelope `eventId`.

Command IDs created by this context use `cmd-<uuid-v7>` form. Correlation IDs use
`corr-<uuid-v7>` form. API `Idempotency-Key` headers are UUID-v7 shaped and are
stored directly; internal commands fold canonical material as documented in
`docs/08-contracts/api/payment-channel.md`.

## Accepted commands

| Command | Sender / Trigger | Produced event(s) | Idempotency material |
|---|---|---|---|
| `CreateChannelOrder` | Payment capture handoff | `ChannelOrderCreated` | API header direct; folds `paymentIntentId + businessRef + purpose + channel + amount + sourceCommandId` |
| `SubmitChannelOrder` | Payment Channel application/ops | `ChannelOrderSubmitted`, optional accepted/succeeded/failed/missed facts | `channelOrderId + submitAttemptNo + requestFingerprint` |
| `QueryChannelOrder` | Payment Channel application/ops | `ChannelOrderQueryRecorded`, optional `ChannelOrderRecoveryDetected` | `channelOrderId + queryAttemptNo` |
| `CreateChannelRefund` | Payment refund handoff | `ChannelRefundCreated` | API header direct; folds `refundId + channelOrderId + originalChannelTransactionId + amount` |
| `SubmitChannelRefund` | Payment Channel application/ops | `ChannelRefundSubmitted`, optional succeeded/failed/missed facts | `channelRefundId + submitAttemptNo + requestFingerprint` |
| `QueryChannelRefund` | Payment Channel application/ops | `ChannelRefundQueryRecorded`, optional `ChannelRefundRecoveryDetected` | `channelRefundId + queryAttemptNo` |
| `GenerateChannelStatement` | Operations endpoint | `ChannelStatementGenerated` | API header direct; folds `channel + statementDate + currency + seedVersion` |
| `FreezeChannelStatement` | Operations endpoint | `ChannelStatementFrozen` | API header direct; folds `channelStatementId + statementHash` |
| `MatchStatementLine` | Statement matching | `ChannelStatementLineMatched` | `channelStatementId + statementLineId + matchRuleVersion` |
| `OpenReconciliationDiscrepancy` | Statement matching or Finance feedback | `ReconciliationDiscrepancyOpened` | `channelStatementId + statementLineId + differenceType + evidenceHash` |
| `AttachFinanceCase` | Finance feedback | `ReconciliationDiscrepancyLinkedToFinanceCase` | `discrepancyId + financeReconciliationCaseId` |
| `ResolveReconciliationDiscrepancy` | Operations/manual action | `ReconciliationDiscrepancyResolved` | API header direct; folds `discrepancyId + resolutionStatus + resolutionRef + expectedVersion` |

## Consumed upstream events

Payment Channel consumes no upstream event stream in Wave A. Payment handoff is
command/API driven with explicit `channelRef` material, and Finance feedback is
through the discrepancy endpoint or existing Finance case references. This avoids
implicit consumers outside the subscription matrix.
