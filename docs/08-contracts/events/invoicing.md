# Invoicing — Events & Commands

Last updated: 2026-07-10

## Scope and Wave-A rulings

This contract covers the ADR-0003 Wave-A Invoicing event surface from
`docs/02-domains/invoicing.md`: invoice title CRUD, deterministic SIM blue
invoice issuance, red-flush observations, and read-only itinerary projections.
Reimbursement export events and write-model itinerary events are deferred unless
explicitly marked below.

Wave-A rulings:

- Blue e-invoice issuance uses only the deterministic, seedable SIM tax-bureau
  gateway. SIM acceptance/rejection is a pure function of normalized request
  material and optional `simSeedRef`; no real tax-bureau network exists.
- Invoicing consumes the existing Post Sales true refund-completion fact
  `PostSalesApplied`. When it observes a refund for an order with an issued blue
  invoice and no completed red flush, it publishes an Invoicing-side observation
  event. **RULING:** Post Sales does not add a same-wave blocker hook; this is a
  recorded violation/telemetry fact to be tightened in a later wave.
- Itinerary receipts are generated through a read-only projection endpoint in the
  HTTP API. No public state-changing itinerary command is added in this wave;
  the `ItineraryReceiptGenerated` event is reserved for future write-model
  activation and is not produced by the Wave-A GET projection.

All payload fields are camelCase, all enum values are SCREAMING_SNAKE_CASE, and
all timestamps are RFC3339 UTC. Money is `{currency, minorUnits}`. Event envelope
fields follow `docs/08-contracts/messaging.md` and
`docs/08-contracts/shared-primitives.md`; `eventType` equals the section name,
`producer` is `invoicing`, and `schemaVersion` is `1`.

## Event identity and command idempotency

### Deterministic eventId rules

Invoicing producers MUST assign deterministic event IDs per aggregate transition.
The UUID-v7-shaped value is generated by folding the seed material below into the
UUID-v7 random bits while preserving the timestamp component from the transition
`occurredAt`. The envelope value is prefixed as `evt-<uuid-v7>` when the bus
adapter uses prefixed IDs.

| Event family | Seed material |
|---|---|
| Invoice title events | `invoicing:<eventType>:<titleId>:<version>` |
| E-invoice request and blue invoice events | `invoicing:<eventType>:<invoiceRequestId>:<aggregateVersion>` |
| SIM gateway result events | `invoicing:<eventType>:<gatewayRequestId>:<gatewayResultHash>` |
| Red-flush events | `invoicing:<eventType>:<redFlushId>:<aggregateVersion>` |
| Refund red-flush observation events | `invoicing:<eventType>:<postSalesCaseId>:<refundFactEventId>:<observationVersion>` |
| Future itinerary write-model events | `invoicing:<eventType>:<itineraryReceiptId>:<receiptVersion>` |

If the same command or consumed upstream event is replayed and no new aggregate
transition occurs, no new event is emitted. Consumers still deduplicate by
envelope `eventId`.

### Command identity, prefixes, and material folding

| Wire value | Format | Rule |
|---|---|---|
| API `Idempotency-Key` | UUID-v7 shape | Used unchanged for external HTTP replay checks. |
| `sourceCommandId` | `cmd-<uuid-v7>` | Folded from the command UUID for envelopes/timelines. Internal bus commands also use this prefix. |
| `correlationId` | `corr-<uuid-v7>` | Propagated from request/upstream envelope; unprefixed UUIDs are folded to this wire form. |
| `causationId` | `cmd-<uuid-v7>` or `evt-<uuid-v7>` | Command-caused events use the command ID; consumed-event reactions use the upstream event ID. |

Business idempotency is enforced by normalized material, not only by command
UUID. Normalization trims strings, normalizes case, sorts arrays, uses
`currency + ':' + minorUnits` for Money, encodes timestamps as RFC3339 UTC, and
hashes canonical JSON with SHA-256.

| Command | Idempotency material |
|---|---|
| `CreateInvoiceTitle` | `accountId + titleType + normalizedTitleName + taxIdentityHash? + contactHash? + bankAccountHash?` |
| `UpdateInvoiceTitle` | `titleId + expectedVersion + mutableTitleFieldsHash` |
| `SetDefaultInvoiceTitle` | `accountId + titleId + commandPurpose:SET_DEFAULT` |
| `DeactivateInvoiceTitle` | `titleId + expectedVersion + reason` |
| `RequestEInvoice` | `orderId + titleId + titleVersion + invoiceScope hash + amountBasisHash + recipientEmailHash? + simSeedRef?` |
| `AttachAmountBasis` | `invoiceRequestId + revenueRecognitionIdsHash + amountBasisHash` |
| `SubmitEInvoice` | `invoiceRequestId + gatewayProfile + submitAttemptNo + requestFingerprint` |
| `RecordGatewayAccepted` / `RecordGatewayRejected` / `RecordGatewayFailed` | `gatewayRequestId + gatewayStatus + gatewayAcceptedAt?/rejectionCode?/failureClass?` (single collapsed rule, identical to `api/invoicing.md`) |
| `MarkEInvoiceIssued` | `gatewayInvoiceNumber + originalRequestId` |
| `RequestRedFlush` | `originalInvoiceId + postSalesCaseId + refundScopeHash` |
| `CompleteRedFlush` | `redInvoiceNumber + originalInvoiceId` |
| `ObserveRefundWithoutRedFlush` | `postSalesCaseId + orderId + refundFactEventId + originalInvoiceIdsHash` |
| `ExpireEInvoiceRequest` | `invoiceRequestId + expiryDeadlineAt` |
| `SubmitRedFlush` | `redFlushId + gatewayProfile + submitAttemptNo + requestFingerprint` |
| `RecordRedFlushAccepted` / `RecordRedFlushRejected` / `RecordRedFlushFailed` | `redFlushGatewayRequestId + gatewayStatus + acceptedAt?/rejectionCode?/failureClass?` (single collapsed rule, mirroring blue-ticket gateway result recording) |

### AmountBasis

| Field | Type | Required | Description |
|---|---|---|---|
| `basisType` | enum | yes | `REVENUE_RECOGNITION`, `FINANCE_INVOICE`, or `MANUAL_APPROVED_SNAPSHOT`. |
| `revenueRecognitionIds` | string[] | no | Finance Settlement revenue recognition IDs. |
| `financeInvoiceId` | string | no | Finance Settlement invoice/reference when applicable. |
| `taxLines` | array[object] | yes | Tax line snapshots with `taxCode`, `taxRateBasisPoints`, `taxableAmount` Money, and `taxAmount` Money. |
| `totalAmount` | Money | yes | Total positive invoice amount. |
| `amountBasisHash` | string | yes | SHA-256 of the canonical Finance Settlement amount snapshot. |

### SimGatewayResult

| Field | Type | Required | Description |
|---|---|---|---|
| `gatewayProfile` | string | yes | SIM gateway profile, normally `SIM_TAX_BUREAU_CN_V1`. |
| `gatewayRequestId` | string | yes | Deterministic request ID created by Invoicing. |
| `simSeedRef` | string | no | Optional deterministic seed reference used by tests/replay. |
| `gatewayStatus` | enum | yes | `ACCEPTED`, `REJECTED`, or `FAILED`. |
| `gatewayAcceptedAt` | RFC3339 UTC | no | Time SIM accepted the request. |
| `rejectionCode` | string | no | Stable business rejection code when status is `REJECTED`. |
| `failureClass` | string | no | Stable technical failure class when status is `FAILED`. |

## Notification and audit touchpoints

Notification may consume `EInvoiceAccepted`, `EInvoiceRejected`, `EInvoiceFailed`,
`EInvoiceIssued`, `RedFlushRejected`, `RedFlushFailed`, and `RedFlushCompleted`
for user/business-contact messages. Customer Service may consume all lifecycle
facts to append safe timeline entries. Admin & Audit consumes
`RefundWithoutRedFlushObserved` for governance; Invoicing may also invoke
Admin & Audit's existing `RecordAuditEntry` command for sensitive title changes
and SIM anomalies. Post Sales consumption of `RedFlushCompleted` as a refund
continuation/blocking signal is explicitly deferred; no Post Sales consumer is
required in Wave A.

## Existing-domain contract increments

This file adds Invoicing as a consumer/producer only. The sole cross-context
existing-domain dependency that affects behavior is consumption of
`PostSalesApplied`; the Post Sales event name and payload remain unchanged.
