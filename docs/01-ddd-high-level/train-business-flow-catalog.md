# Train Ticket 业务流全景目录

Last updated: 2026-06-28

## 目的

这份文档补充 `docs/01-ddd-high-level/train-ddd-business-flows.md`，用于在重构前把火车售票系统可能涉及的业务流尽量摊开。它不以当前服务名为边界，也不绑定任何实现语言，只描述业务从哪里开始、由谁决策、产生什么业务事实。

如果后续要把系统升级成通用出行平台，覆盖大巴、网约车、飞机、轮船和联乘中转，参见 `docs/01-ddd-high-level/general-travel-ddd.md`。本文仍以火车票务为主。

本文的目标是：

1. 形成完整的业务流地图，避免只围绕当前代码里已经写死的接口做重构。
2. 标出哪些流是核心交易闭环，哪些是生产系统必备能力，哪些是可后置扩展。
3. 为后续事件风暴、上下文映射、聚合建模和多语言实现拆分提供输入。

## 分级说明

| 等级 | 含义 |
|---|---|
| P0 | 核心闭环。没有这些流，系统不能完成基本售票、乘车和售后。 |
| P1 | 生产必备。没有这些流，真实运营会频繁失败或需要大量人工兜底。 |
| P2 | 扩展能力。可作为后续业务增长、渠道协同或精细化运营能力。 |

## 业务全景

火车售票系统不是单纯的“查询余票、创建订单、支付”。它至少包含八类业务活动：

1. 供给侧准备：维护站点、线路、车次、运行图、票价、席别、车厢、票额。
2. 客户侧准备：账号、实名、乘车人、购票限制、风控。
3. 售前交易：搜索、推荐、报价、资格校验、余票确认。
4. 售中交易：下单、占座、锁票、支付、出票。
5. 乘车履约：取票、检票、进站、乘车、出站、行程完成。
6. 售后变更：退票、改签、变更到站、退款、差价结算。
7. 异常处置：晚点、停运、车次调整、大客流、支付回调异常、库存不一致。
8. 平台运营：通知、审计、对账、清算、客服、报表、权限和后台审批。

## 候选限界上下文

| 上下文 | 负责的业务事实 |
|---|---|
| Account | 登录账号、凭证、账号状态、渠道账号绑定。 |
| Passenger Profile | 乘车人、实名证件、优惠资质、乘车限制。 |
| Rail Catalog | 站点、线路、车站关系、车型、车厢、席别等基础目录。 |
| Operation Plan | 运行图、车次计划、经停计划、开售计划、停售计划。 |
| Fare Product | 票价、席别产品、优惠规则、手续费规则、销售限制。 |
| Inventory | 票额、座席、区间占用、锁票、释放、候补兑现。 |
| Shopping | 站站查询、车次查询、联程推荐、报价快照。 |
| Sales Order | 订单、订单项、乘车人订单、订单状态机。 |
| Payment | 支付单、退款单、支付回调、支付超时、差价收退。 |
| Ticketing | 出票、电子票、票面凭证、取票状态、票号。 |
| Travel Fulfillment | 检票、进站、车上验票、补票、出站、行程完成。 |
| Post Sales | 退票、改签、变更到站、部分退改、手续费计算。 |
| Disruption | 晚点、停运、车次变更、旅客保护方案、免手续费策略。 |
| Ancillary Service | 餐饮、保险、托运、无障碍服务、车站服务。 |
| Notification | 业务通知、模板、发送记录、失败重试、订阅偏好。 |
| Customer Service | 工单、申诉、人工退款、争议处理、凭证补发。 |
| Risk Control | 限流、反刷、黑名单、重复行程、异常支付和异常退票。 |
| Finance Settlement | 支付对账、退款对账、渠道结算、收入确认、发票。 |
| Admin & Audit | 后台权限、操作审计、配置审批、数据订正。 |
| Reporting | 销售报表、客流报表、收入报表、库存使用分析。 |

## 业务流目录

### A. 供给侧和运营计划

| ID | 等级 | 业务流 | 触发 | 核心结果 | 主要上下文 |
|---|---|---|---|---|---|
| A01 | P0 | 站点和线路维护 | 运营人员新增或调整站点、线路 | 站点、线路、站间关系可用于查询和车次编排 | Rail Catalog |
| A02 | P0 | 车型、车厢和席别维护 | 运营人员维护列车物理能力 | 车型、车厢、座位布局、席别产品具备统一定义 | Rail Catalog |
| A03 | P0 | 运行图和车次计划发布 | 运营人员发布某日期的车次计划 | 车次、始发终到、经停、到发时刻可售前查询 | Operation Plan |
| A04 | P0 | 票价和手续费规则发布 | 票务运营维护价格策略 | 不同区间、席别、旅客资质有可计算票价 | Fare Product |
| A05 | P0 | 票额初始化和区间库存生成 | 车次开售前初始化库存 | 按车次、日期、席别、区间形成可售票额 | Inventory |
| A06 | P1 | 销售日历和开售窗口管理 | 运营设置预售期、开售时刻、停售时刻 | 系统知道某车次某席别何时允许售卖 | Operation Plan |
| A07 | P1 | 渠道配额分配 | 运营按渠道配置票额或限售规则 | Web、App、窗口、代理渠道有明确可售范围 | Inventory, Sales Channel |
| A08 | P1 | 临时加开、重联、换编组 | 运力临时调整 | 新增或调整车次供给，库存和已售订单被同步保护 | Operation Plan, Inventory |
| A09 | P1 | 停售和限售配置 | 运营因管控、故障或政策停售 | 被影响车次、区间、席别停止销售或限制销售 | Operation Plan, Fare Product |
| A10 | P2 | 运营配置审批 | 高风险配置变更提交审批 | 价格、库存、运行图等变更留下审批事实 | Admin & Audit |

## 关键端到端链路

### 主链路：从供给到乘车完成

1. 运营发布站点、线路、车型、席别、运行图、车次和票价。
2. 系统按车次日期生成库存，配置开售窗口和渠道可售范围。
3. 用户登录并维护乘车人，实名和优惠资质通过校验。
4. 用户查询车次或联程方案，系统返回可售状态、价格和余票。
5. 用户创建订单，订单校验乘车资格、冲突行程和销售限制。
6. 库存上下文锁定区间票额并分配座席。
7. 支付上下文完成收款，订单上下文推进到已支付。
8. Ticketing 生成车票，通知上下文发送出票结果。
9. 旅客凭证件或电子票进站、乘车、出站。
10. 行程完成后，车票进入完成状态，财务可做收入确认。

### 售后链路：退票

1. 用户选择已出票票项发起退票。
2. Post Sales 查询票证状态、发车时间、取票状态和退票规则。
3. Fare Product 计算手续费，Payment 计算应退金额。
4. Ticketing 作废车票，Inventory 释放可再售区间库存。
5. Payment 创建退款单并等待渠道结果。
6. Sales Order 汇总订单状态，Notification 通知用户。

### 售后链路：改签

1. 用户选择原票和目标车次、席别、日期。
2. 系统校验原票是否允许改签，以及目标方案是否可售。
3. Inventory 锁定目标票额，Post Sales 计算旧票和新票差价。
4. Payment 完成补款或退款处理。
5. Ticketing 作废旧票并生成新票。
6. 若任一步失败，系统释放新库存，保留或恢复旧票状态，并记录补偿事件。

### 异常链路：停运

1. 运营发布停运事件。
2. Operation Plan 将车次停售，Shopping 不再返回普通可售方案。
3. Disruption 识别所有受影响订单、候补单和附加服务。
4. Post Sales 应用免手续费退票或保护性改签规则。
5. Payment 批量退款，Notification 告知旅客可选动作。
6. Reporting 和 Audit 记录影响范围、处理进度和未完成补偿。

### 候补链路

1. 用户在无票场景提交候补需求。
2. 系统校验乘车人、冲突行程、候补截止时间和支付担保。
3. 候补需求进入队列，按规则排序。
4. 退票、改签或运营放票释放库存后，Inventory 触发候补兑现。
5. 候补成功时自动占座、扣款或确认付款、出票和通知。
6. 候补失败或到期时关闭需求，退款或释放担保资金。

## 当前代码缺口视角

结合 `docs/01-ddd-high-level/train-ddd-business-flows.md` 中恢复出的主干链路，当前系统已经显性或隐性覆盖了部分查询、下单、支付、取消、改签、餐饮、托运、保险、通知和候补能力，但距离完整火车售票系统仍有明显缺口：

| 缺口 | 影响 |
|---|---|
| 运行图、开售窗口、停售、限售没有成为稳定业务模型 | 查询和售票规则容易继续写死在服务代码里。 |
| 库存仍像普通商品库存，而不是按车次、日期、席别、座位、区间占用建模 | 余票、跨区间售卖、退改释放和候补兑现都会不可信。 |
| 实名、优惠资质、重复行程、风控限制没有完整前置 | 下单链路会混入大量临时校验，难以解释失败原因。 |
| 检票、进站、车上补票、出站等履约事实缺失 | 订单只能表达支付结果，不能表达旅客是否真的使用了票。 |
| 晚点、停运、经停变化等运营异常没有独立上下文 | 退改和通知无法区分用户原因与铁路原因。 |
| 财务对账、清算、发票、收入确认缺失 | 支付成功不等于财务闭环完成。 |
| 后台审计、权限、人工干预不足 | 后续生产化后无法安全处理例外场景。 |

## 重构时的业务优先级

第一阶段应先完成 P0 闭环：

1. Rail Catalog、Operation Plan、Fare Product 建立可售供给。
2. Passenger Profile 完成乘车人、实名和购票资格。
3. Shopping 完成查询、报价、可售性解释。
4. Sales Order、Inventory、Payment、Ticketing 完成下单、占座、支付、出票。
5. Post Sales 完成取消、退票、改签和退款。
6. Notification、Admin & Audit 完成关键通知和可追溯操作。

第二阶段补 P1 生产能力：

1. 开售窗口、停售限售、渠道配额。
2. 联程、邻近站、候补。
3. 取票、检票、车上验票、行程完成。
4. 晚点、停运、旅客保护、批量退款。
5. 支付退款对账、收入报表、库存差异监控。
6. 客服工单、人工干预、后台权限。

第三阶段再扩展 P2 能力：

1. 团体票、企业票、B2B 开放 API。
2. 个性化推荐、会员积分、营销触达。
3. 贵宾厅、接送站等车站增值服务。
4. 数据归档、合规删除、复杂运营审批。
